# 显示管道的像素传输：数据流 vs 控制流

> 整个 KMS 管道的目的就是把 framebuffer 中的像素数据送到 panel 显示。但数据流和控制流是**两条完全不同的路径**。

---

## 一、数据流 vs 控制流

```
┌─────────────────────────────────────────────────────────────────────┐
│                        控制流（CPU 写寄存器）                          │
│  DRM → plane atomic_update（写 DMA 地址/格式/使能）                    │
│       → CRTC atomic_flush（cfg_done 锁存所有 shadow 寄存器）            │
│       → encoder enable（配置 DSI PHY/协议参数）                        │
│       → bridge enable（转发使能信号）                                   │
│       → panel enable（开背光）                                         │
├─────────────────────────────────────────────────────────────────────┤
│                        数据流（纯硬件，CPU 不参与）                      │
│  DDR fb → VOP2 DMA Engine → 图层合成 → VP 时序生成                     │
│         → 并行像素+时序信号 → Encoder → 协议转换 → PHY → Panel          │
│         ↑ 每个帧周期硬件自动循环                                        │
└─────────────────────────────────────────────────────────────────────┘
```

**关键认知**：CPU 只在 atomic commit 时写一次寄存器，之后**纯硬件**在每个帧周期（通常 60Hz）自动完成像素搬运、合成、输出。数据流的唯一源头是 DDR 中的 framebuffer。

---

## 二、数据流详解：像素从 DDR 到 Panel 的完整路径

### 2.1 阶段一：VOP2 DMA 读取（Plane 层）

**硬件行为**（VOP2 内部，CPU 不参与）：

每个 plane（vop2_win）内部有一个 DMA 引擎。当 VOP2 VP 开始扫描一帧时：
1. DMA 根据 plane 的 `yrgb_mst` 寄存器（framebuffer 基地址）和 `yrgb_vir` 寄存器（stride）从 DDR 读像素
2. 根据 `act_info` 寄存器（宽/高）和 `dsp_info` 寄存器（显示位置）做裁剪和缩放
3. 输出到 VP 内部的图层混合器

**CPU 做的事**（只做一次，在 commit 时）：

`vop2_plane_atomic_update()`（[vop2.c:3281](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L3281)）— 把 DMA 参数写入 VOP2 窗口的 shadow 寄存器：
```c
VOP_WIN_SET(vop2, win, yrgb_mst,  vpstate->yrgb_mst);   // FB 基地址
VOP_WIN_SET(vop2, win, yrgb_vir,  fb->pitches[0] / 4);   // stride
VOP_WIN_SET(vop2, win, act_info,  ...);                  // 源宽高
VOP_WIN_SET(vop2, win, dsp_info,  ...);                  // 目标位置
VOP_WIN_SET(vop2, win, enable, 1);                       // 使能此窗口
```

### 2.2 阶段二：VP 图层混合与时序生成（CRTC 层）

**硬件行为**：

1. **图层混合**：6 个 Layer Mixer 硬件模块将多个 window 的输出按 zpos 顺序混合（`pre_mult_alpha`、`coverage` 等 blend mode）
2. **后处理**：HDR tone mapping、Gamma LUT、Cubic LUT、Dither
3. **时序生成**：根据 CRTC 的 `adjusted_mode` 生成视频时序信号——HSYNC、VSYNC、DEN（data enable，像素有效标志）、像素时钟（DCLK）

**CPU 做的事**：

| CPU 操作 | 函数 | 位置 |
|----------|------|------|
| 排序所有 plane → 写 OVL_LAYER_SEL 寄存器 | `vop2_crtc_atomic_begin` | [vop2.c:5390](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L5390) |
| 配置 alpha 混合 | `vop2_setup_alpha` | [vop2.c:5099](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L5099) |
| 配置层延迟补偿 | `vop2_setup_dly_for_vp` | [vop2.c:5325](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L5325) |
| 写 cfg_done → 硬件锁存 | `vop2_crtc_atomic_flush` | [vop2.c:5775](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L5775) |
| 配置时序（HSYNC/VSYNC 等） | `vop2_crtc_atomic_enable` | [vop2.c:4565](../../kernel/drivers/gpu/drm/rockchip/rockchip_drm_vop2.c#L4565) |

**时序生成的真实含义**：

VP 根据 `adjusted_mode` 的字段生成精确的同步脉冲。先看 DRM mode 各字段的时序位置：

```
hdisplay    = 一行中有效像素个数
hsync_start = hdisplay + hfront_porch     ← 前肩之后，HSYNC 开始
hsync_end   = hsync_start + hsync_len    ← HSYNC 结束
htotal      = hsync_end + hback_porch    ← 后肩之后，下一行开始
```

一行像素的完整周期（VESA 标准顺序，从有效像素开始）：
```
┌──────────┬──────────┬──────────┬──────────┐
│ hdisplay │ 前肩(hfront)│ HSYNC脉冲 │ 后肩(hback)│ → 下一行的 hdisplay
│ (有效像素)│  DEN=0   │ DEN=0   │  DEN=0   │
└──────────┴──────────┴──────────┴──────────┘
```

后肩在 HSYNC 脉冲**之后**、下一行 hdisplay **之前**。"后"=back of the sync pulse。前肩在有效像素**之后**、HSYNC **之前**。"前"=front of the sync pulse。

#### 硬件视角（以 HSYNC 为原点）

上面的描述是从 VESA 软件规范出发的。但从硬件计数器角度看，HSYNC 才是自然的起点——VOP2 内部的列计数器由 HSYNC 脉冲触发复位为 0，然后自增计数到 htotal：

```
HSYNC 脉冲来时列计数器清零：

计数器: 0 ──────────────────────────────────────────→ htotal-1 → 0（下一行）
        ├──────┤├──────────────┤├──────┤├────────────┤├──────┤
        HSYNC   │  后肩(hback)  │hdisplay│  前肩(hfront) │ HSYNC
        (DEN=0)  │  (DEN=0)     │(DEN=1) │  (DEN=0)     │ (下一行)
                │                  ↑                    │
                │           有效像素区域                   │
                └──────────────────────────────────────┘
                         硬件状态机顺序（以 HSYNC 为零点）
```

每个 PCLK 周期列计数器 +1，按区间驱动 DEN 信号：
- `[0, hsync_len)`：DEN 低（同步进行中）
- `[hsync_len, hsync_len + hback_porch)`：DEN 低（后肩，panel 准备接收）
- `[hsync_len + hback_porch, hsync_len + hback_porch + hdisplay)`：**DEN 高**（输出有效像素）
- `[hsync_len + hback_porch + hdisplay, htotal)`：DEN 低（前肩，消隐）

这就是为什么**后肩的长度会影响画面在屏幕上的水平位置**——后肩越长，有效像素的起始位置越靠右（偏移越大）。前肩则影响有效像素结束后的消隐长度。

一帧同理（以 VSYNC 为零点）：
```
VSYNC → 后肩行 → vdisplay → 前肩行 → 下一个 VSYNC
```

上面这段描述里，前肩、HSYNC、后肩看起来完全是三种不同的东西。但在物理信号线上它们是**一样的**——VP 只发出这几根线：
```
PCLK, HSYNC, VSYNC, DEN, R[7:0], G[7:0], B[7:0]
```
前肩和后肩没有独立的信号线，它们在物理上都是 DEN=0、HSYNC 不变的那段消隐区，肉眼无法区分。那为什么寄存器里要分成三个独立参数，而不是一个"总消隐长度"？

因为它们对画面的物理效果不同，每个参数控制一个独立变量：

| 参数 | 改了影响什么 |
|------|-------------|
| **后肩 (hback_porch)** | 有效像素在屏幕上的**水平起点位置**（偏移量）。后肩越长，画面越靠右 |
| **前肩 (hfront_porch)** | 有效像素结束后的空闲时长。用来吸收帧间抖动、给 panel 像素电路复位 |
| **HSYNC 长度 (hsync_len)** | 同步脉冲宽度。太窄 panel 检测不到，太宽浪费带宽 |
| **hdisplay** | 一行显示多少个有效像素 |

本质上是四个独立变量解一道方程：
```
htotal = hdisplay + hfront_porch + hsync_len + hback_porch
```
如果寄存器只提供一个"总消隐"，panel 工程师只能调总长度，却没法独立控制画面水平位置——不知道这坨消隐该放在同步脉冲前面还是后面。三个独立参数才能精确定义每一段。

### 2.3 阶段三：Encoder 协议转换（Encoder 层）

这是你问的核心——**encoder 不产生像素，它只做格式转换**。

VOP2 VP 输出（并行信号）:            MIPI DSI Encoder 输出（串行差分信号）:
                                    
  [24-bit RGB 并行总线]              DSI Packet:
  R[7:0] ────────────               ┌─ 短包(4B): 同步事件
  G[7:0] ────────────    ──→        ├─ 长包(6+N*3B): 一行像素数据
  B[7:0] ────────────               └─ 校验和
  PCLK ──────────────               
  HSYNC ─────────────               每个像素 24bit，每行分成多个 DSI 数据包
  VSYNC ─────────────               由 D-PHY 物理层以 MIPI 差分信号发出
  DEN ───────────────

**CPU 做的事**（DSI encoder enable 时，[dw-mipi-dsi.c:1324](../../kernel/drivers/gpu/drm/rockchip/dw-mipi-dsi.c#L1324)）：

```c
// 1. DSI PHY 上电和时钟初始化 (pre_enable)
dw_mipi_dsi_pre_enable(dsi);       // [L1345] 配置 D-PHY lanes, clock lane, PLL

// 2. Panel 上电 (信号还没来)
drm_panel_prepare(dsi->panel);     // [L1347]

// 3. DSI Host 开始工作 (enable) — 从 VP 的并行总线取数据 → 打包 → 送 PHY
dw_mipi_dsi_enable(dsi);           // [L1348] 使能 DSI 视频模式

// 4. Panel 使能输出 (信号已经稳定)
drm_panel_enable(dsi->panel);      // [L1354] 开背光
```

`dw_mipi_dsi_enable()` 里面做的事：
- 配置 DSI 数据包格式（video mode vs command mode、burst mode vs non-burst）
- 使能 DSI host 控制器：开始从 VP 并行总线采样像素、按 DSI 协议打包、推送到 D-PHY 发送
- **关键**：encoder 不"创造"任何像素——它只是 VP 和 PHY 之间的协议转换器

### 2.4 阶段四：PHY 物理传输

D-PHY（或 LVDS PHY）是纯硬件。MIPI D-PHY 把 DSI host 输出的并行数据转换成高速低压差分信号（HS mode），在每对 data lane 上以差分信号传输。CPU 只需在 `pre_enable` 阶段配置好 lane 数量、速率，之后硬件自动工作。

### 2.5 阶段五：Panel 接收并显示

Panel 端的 DSI 接收器解析数据包，把像素写入 panel 内部的帧缓冲，LCD 驱动电路驱动液晶分子偏转/OLED 发光。CPU 只需控制电源（prepare）和背光（enable），不需要参与逐像素。

## 四、回答：encoder enable "开始发视频流"到底是什么意思？

这个表述不准确。更精确的描述是：

**encoder enable = 打开 VP 和 PHY 之间的"阀门"**

```
VOP2 VP                                                           D-PHY
  │                                                                 │
  │  24-bit RGB 并行总线 + PCLK + HSYNC + VSYNC + DEN                │
  │  (VP 已经在跑——如果还没人接收，信号就是悬空的)                      │
  │                                                                 │
  │    ┌────────── DW-MIPI-DSI Encoder ─────────┐                   │
  │    │                                         │                   │
  └────┼─→ 采样并行像素 ──→ 打包 DSI 数据包 ──→ D-PHY 接口 ──→ MIPI 差分对
       │                                         │
       └─────────────────────────────────────────┘
```

三段式时序：

```
时间线:
  pre_enable (PHY 上电+时钟准备)
       │
       │  VP 已经在产生像素和时序，但 DSI host 控制器还没使能
       │  → 像素数据在 host 前端被忽略/丢弃
       │
  enable (DSI host 开始工作)
       │
       │  Host 控制器开始采 VP 并行总线 → 数据打包 → 推送到 PHY
       │  → MIPI 差分对上开始有信号
       │  *** 这就是"开始发视频流"的真正意思 ***
       │
       │  但 encoder 不是"产生"视频流——它只是把 VP 的信号转换成
       │  另一种电气/协议格式送出去
       │
  panel enable (背光打开)
       │
       ▼
```

**所以 encoder enable 的精确含义是**：使能协议转换器，让它开始接收 VP 已经在产生的并行像素信号、并按目标协议（DSI/LVDS/HDMI）转成串行差分信号从 PHY 发出去。

**谁真正产生像素？** VOP2 VP（CRTC）的扫描引擎。它在 `atomic_enable` 时被释放 standby，开始按配置的时序输出像素时钟和行/场同步信号。但此时如果没有 encoder enable，这些并行信号会被忽略。

**谁产生视频内容？** DDR 中的 framebuffer（由应用/GPU 渲染）。VOP2 DMA 引擎把像素从 DDR 搬运出来、合成、输出——这整个过程 CPU 不参与。

```
                    CPU 控制流                          │  硬件数据流（每个帧周期自动）
                                                       │
  atomic_commit 开始                                    │
  │                                                    │
  ├─ commit_modeset_disables                           │
  │   ├─ bridge_disable      (panel 关背光)             │
  │   ├─ encoder->disable    (DSI host 停)              │
  │   ├─ bridge_post_disable (PHY 断电)                 │
  │   └─ crtc->atomic_disable(VP 停 + 关所有 plane)     │  VP 停止扫描
  │                                                    │
  ├─ commit_planes                                    │
  │   ├─ atomic_begin        (排序、layer mixer)        │
  │   ├─ atomic_update×N     (写 DMA 地址/使能窗口)      │
  │   └─ atomic_flush        (cfg_done 锁存)            │  ← 此时 shadow 寄存器已更新
  │                                                    │     但 VP 还在 standby
  ├─ commit_modeset_enables                            │
  │   ├─ crtc->atomic_enable (配置时序, 释放 standby)    │  → VP 开始扫描！
  │   │                           ★ 此时并行总线上开始    │     像素时钟开始运行
  │   │                             出现有效的像素+时序    │     DMA 引擎开始搬运像素
  │   │                                                 │     从 DDR fb → VP 输出
  │   │                                                 │     但 MIPI 差分对上没有信号
  │   │                                                 │     (DSI host 还没 enable)
  │   ├─ bridge_pre_enable   (PHY 上电, 时钟 ready)      │
  │   ├─ encoder->enable     (DSI host 开始工作)         │     → MIPI 差分对开始有信号
  │   │                           ★ 从并行总线取数据      │        像素被打包成 DSI 数据包
  │   │                             打包 → 推送到 PHY     │        通过 D-PHY 串行发出
  │   │                                                 │        但 panel 背光还没开
  │   └─ bridge_enable       (panel 开背光)              │     → 用户看到画面
  │                                                    │
  └─ wait_for_vblanks (等一帧确认)                       │     硬件继续每帧自动循环：
                                                       │       DMA fb → 合成 → VP 输出
  commit 结束                                           │       → DSI → panel
                                                       │      直到下一次 commit 改变寄存器
```

## 六、关键要点

1. **数据流是纯硬件的**：CPU 写一次寄存器后，VOP2 硬件在每个帧周期（60Hz）自动 DMA 读 DDR fb → 合成 → 输出。数据流的唯一源头是 DDR framebuffer。

2. **控制流是单次的**：atomic commit 时 CPU 按顺序写寄存器——先配置数据路径（plane→CRTC），再配置输出路径（encoder→bridge→panel）。

3. **cfg_done 是"交接点"**：`atomic_flush` 写 `cfg_done` 后，所有 shadow 寄存器在下个 vblank 原子锁存到 active 寄存器。这意味着 plane、CRTC 的配置**不会立即生效**，而是等到下个帧开始才生效。

4. **Encoder 不产生视频**：VP（CRTC）产生并行像素+时序信号。Encoder 只是协议转换器——把并行信号转成 DSI/LVDS/HDMI 格式发到 PHY。

5. **commit_planes 和 modeset_enables 是两个阶段**：普通 page flip（不换分辨率/不开关 CRTC）只走 commit_planes，不触发 modeset enable/disable。这避免了不必要的 encoder/panel 操作。

## 七、为什么 CRTC（VP）不直接输出串行信号？

### 7.1 芯片物理架构：数字逻辑 vs 模拟电路

```
┌──────────────────── 芯片内部 ────────────────────┐
│                                                    │
│  VOP2（纯数字综合）       DSI/LVDS/HDMI PHY（模拟定制）│
│  ────────────────         ──────────────────────── │
│  · 标准数字单元库          · PLL（时钟倍频到 GHz）     │
│  · ~150MHz 像素时钟        · 差分驱动器（LVDS/HSD）    │
│  · 单端 CMOS 电平          · 阻抗匹配/端接            │
│  · 布局在 SoC 深处         · 布局在引脚附近           │
│                                                    │
└────────────────────────────────────────────────────┘
```

VOP2 是用硬件描述语言（Verilog/VHDL）描述、通过标准数字单元库综合出来的纯数字电路。而 MIPI D-PHY 需要 PLL 把参考时钟倍频到 ~1GHz、低压差分驱动、阻抗匹配——这些是模拟/混合信号电路，必须用定制晶体管实现，和标准数字单元库完全不同的工艺。

### 7.2 IP 复用：一个 VP 配多种 PHY

如果 VP 内部硬编码了 DSI 协议：
- RK3568 的 VP0 就只能接 DSI 屏
- 要支持 LVDS，需要另一个完全不同的 VP 设计
- 要支持 HDMI/DP，又需要完全不同的 VP

**实际上**，VP 输出标准并行 RGB 总线，然后通过 OF graph 在片上接不同的 encoder+PHY：

```
VOP2 VP0 ──→ DSI encoder ──→ D-PHY     → MIPI DSI 屏幕
         ├─→ LVDS encoder ─→ LVDS PHY  → LVDS 屏幕
         ├─→ RGB encoder ──→ 直出并口    → RGB 并口屏
         └─→ HDMI encoder ─→ HDMI PHY   → HDMI 显示器
```

RK3568 的 DT 中通过 `remote-endpoint` 决定 VP 连哪个 encoder——同一颗芯片、同一个 VOP2 IP，不同产品搭配不同屏幕。

### 7.3 并行 RGB 是显示控制器的"通用语言"

所有主流 encoder IP（Synopsys DesignWare DSI/HDMI、Analogix DP、各种 LVDS transmitter）都接受相同的输入接口：

```
信号     │ 含义            │ 所有 encoder 都理解
─────────┼─────────────────┼─────────────────────
PCLK     │ 像素时钟         │ ✓
HSYNC    │ 行同步脉冲       │ ✓
VSYNC    │ 帧同步脉冲       │ ✓
DEN      │ 数据有效标志      │ ✓
R[7:0]   │ 红色分量         │ ✓（或 RGB888/666/565）
G[7:0]   │ 绿色分量         │ ✓
B[7:0]   │ 蓝色分量         │ ✓
```

这是显示器行业标准的视频时序接口（VESA Display Timing Standard）。只要 VP 输出这组信号，任何 encoder 都能接收。

### 7.4 物理布局约束

芯片的模拟 PHY 必须靠近引脚（pad-limited——放在远离引脚的位置会导致寄生电容过大、信号质量下降）。而 VOP2 是纯数字模块，可以放在芯片内部深处。如果 VOP2 直接输出串行信号，那整个 VOP2 也要搬到引脚附近，会严重挤占宝贵的引脚周边面积。

### 7.5 一句话总结

**并行 RGB 接口就是 VP（数字）和 PHY（模拟）之间的物理+逻辑分界线**——它让数字 IP 和模拟 IP 各安其位，各自用最适合的工艺实现，通过一个标准接口松耦合。
