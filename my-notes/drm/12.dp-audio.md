# DPTX 传输音频链路分析

## 概述

RK356x 平台有两套 DP 控制器用于音频传输：

| 控制器 | 兼容串 | 适用芯片 | 音频接口 |
|--------|--------|----------|----------|
| CDN-DP (Cadence) | `rockchip,rk3399-cdn-dp` | RK3399 | I2S + SPDIF |
| Analogix DP (eDP) | `rockchip,rk3568-edp` | RK3568 | I2S + SPDIF |

两者共用同一套 ALSA/DRM 音频框架，差异在于底层寄存器/Firmware 配置方式。

---

## Link Training（链路训练）

Link Training 是 DP 音频传输的**前提条件**——只有链路训练成功建立后，音频数据包才能通过 Main Link 传输。训练失败则整个 DP 链路不可用，音频也就无法工作。

### 训练触发时机

```
触发点: encoder enable
  └── cdn_dp_encoder_enable()              [cdn-dp-core.c#L664]
      └── cdn_dp_enable()                  // 使能 PHY、加载 firmware
      └── cdn_dp_check_link_status()       // 检查已有链路状态
      └── cdn_dp_train_link()              // 需要训练时触发
          [cdn-dp-reg.c#L608]

触发点: 热插拔 work (重训练)
  └── cdn_dp_pd_event_work()               [cdn-dp-core.c#L1083]
      └── cdn_dp_needs_link_retrain()      // 检测是否需要重训练
          └── cdn_dp_train_link()          // 重新训练

触发点: Analogix DP bind 后
  └── analogix_dp_bridge_enable()           [analogix_dp_core.c]
      └── analogix_dp_train_link()
          [analogix_dp_core.c#L838]
```

### CDN-DP Link Training 流程

CDN-DP 有两条训练路径：**Software Training**（优先）→ 失败回退到 **Firmware Training**。

#### 入口函数

[cdn_dp_train_link()](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L608)

```
cdn_dp_train_link()
├── cdn_dp_software_train_link()        // 优先尝试软件训练
│   └── 成功 → 写 SOURCE_HDTX_CAR=0xf, use_fw_training=false
└── 失败 → 回退 firmware training
    ├── cdn_dp_training_start()         // 通过 mailbox 启动 FW 训练
    │   └── 等待 EQ_PHASE_FINISHED 事件
    └── cdn_dp_get_training_status()    // 读取 link rate & lane count
```

#### Software Training 详细流程

[cdn_dp_software_train_link()](kernel/drivers/gpu/drm/rockchip/cdn-dp-link-training.c#L358)

```
cdn_dp_software_train_link()
│
├── 1. 读 DPCD → 协商 link rate & lane count
│   source_max = dp->lanes
│   sink_max   = drm_dp_max_lane_count(dp->dpcd)
│   link.num_lanes = min(source_max, sink_max)
│   rate = min(CDN_DP_MAX_LINK_RATE (HBR2/5.4Gbps), sink_max)
│
├── 2. 写 DPCD: DP_DOWNSPREAD_CTRL (展频 + 8b/10b)
│
├── 3. while(true) — 降速重试循环:
│   │
│   ├── tcphy_dp_set_link_rate(phy, rate, ssc_on)
│   │   └── 配置 USB-C PHY 到目标 link rate
│   │
│   ├── tcphy_dp_set_lane_count(phy, num_lanes)
│   │   └── 配置 PHY lane 数量
│   │
│   ├── 写 DPCD: DP_LINK_BW_SET (rate + lane_count)
│   │
│   ├── cdn_dp_link_training_clock_recovery()   ← CR 阶段
│   │   [cdn-dp-link-training.c#L215]
│   │   │
│   │   ├── cdn_dp_reset_link_train(TP1)
│   │   │   ├── memset(train_set, 0)
│   │   │   ├── cdn_dp_set_signal_levels()  → tcphy_dp_set_phy_config()
│   │   │   ├── cdn_dp_set_pattern(TP1)     → DP_FRAMER_GLOBAL_CONFIG
│   │   │   │   ├── NO_VIDEO                // 训练期间不传视频
│   │   │   │   ├── DP_TX_PHY_TRAINING_ENABLE(1)
│   │   │   │   └── DP_TX_PHY_SCRAMBLER_BYPASS(1)
│   │   │   └── cdn_dp_set_link_train(TP1)  → DP_TRAINING_PATTERN_SET
│   │   │
│   │   └── for(;;) — CR 循环:
│   │       ├── drm_dp_link_train_clock_recovery_delay()  // 100us
│   │       ├── drm_dp_dpcd_read_link_status()            // 读 sink 状态
│   │       ├── drm_dp_clock_recovery_ok()                // CR 完成检查
│   │       │   └── 每个 lane 的 CR_DONE bit 都置位 → 成功返回
│   │       ├── voltage_tries >= 5 → 失败
│   │       ├── max_vswing_tries >= 1 → 失败
│   │       ├── cdn_dp_get_adjust_train()  // 根据 sink 请求调整
│   │       │   └── 取所有 lane 中 max(v, p)
│   │       └── cdn_dp_update_link_train() → DPCD 写 + tcphy 配置
│   │
│   ├── cdn_dp_link_training_channel_equalization()  ← EQ 阶段
│   │   [cdn-dp-link-training.c#L275]
│   │   │
│   │   ├── cdn_dp_select_chaneq_pattern()
│   │   │   ├── TPS3 supported → DP_TRAINING_PATTERN_3
│   │   │   └── else           → DP_TRAINING_PATTERN_2
│   │   ├── cdn_dp_set_pattern(training_pattern)
│   │   ├── cdn_dp_set_link_train(training_pattern)
│   │   │
│   │   └── for tries=0..4 — EQ 循环:
│   │       ├── drm_dp_link_train_channel_eq_delay()  // 400us
│   │       ├── drm_dp_dpcd_read_link_status()
│   │       ├── drm_dp_clock_recovery_ok()  // CR 仍然要保持
│   │       ├── drm_dp_channel_eq_ok()      // EQ 完成 → 成功返回
│   │       │   ├── CHANNEL_EQ_BITS 全部置位
│   │       │   └── LANE_ALIGN_STATUS_UPDATED 对齐
│   │       ├── cdn_dp_get_adjust_train()
│   │       └── cdn_dp_update_link_train()
│   │
│   └── 失败 → cdn_dp_get_lower_link_rate() 降速
│       ├── 5.4G → 2.7G → 1.62G → 失败
│       └── continue (重新尝试训练)
│
└── 4. cdn_dp_stop_link_train()
    ├── cdn_dp_set_pattern(DP_NONE)       // 禁用训练图案
    └── cdn_dp_set_link_train(DISABLE)    // 通知 sink 训练结束
```

#### Firmware Training（回退路径）

[cdn_dp_training_start()](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L536)

```
cdn_dp_training_start()
├── mailbox send: DPTX_TRAINING_CONTROL + LINK_TRAINING_RUN
└── 轮询等待 (超时 500ms, 间隔 20ms):
    ├── mailbox: DPTX_READ_EVENT
    └── event[1] & EQ_PHASE_FINISHED → 成功

cdn_dp_get_training_status()              [cdn-dp-reg.c#L579]
├── mailbox: DPTX_READ_LINK_STAT
└── 读取 status[0]=link_rate, status[1]=num_lanes
```

#### 重训练检测

[cdn_dp_needs_link_retrain()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1065)

```
cdn_dp_needs_link_retrain()
├── !link.rate || !link.num_lanes → false (未训练过)
├── drm_dp_dpcd_read_link_status()
└── !drm_dp_channel_eq_ok() → true (需要重训练)
```

### Analogix DP Link Training 流程

Analogix DP 也有两条路径：**Fast Link Training**（面板支持时）→ 回退 **Full Link Training**。

#### 入口

[analogix_dp_train_link()](kernel/drivers/gpu/drm/bridge/analogix/analogix_dp_core.c#L838)

```
analogix_dp_train_link()
├── dp->fast_train_enable == true
│   └── analogix_dp_fast_link_train()
└── else
    └── analogix_dp_full_link_train()
```

#### Fast Link Training

[analogix_dp_fast_link_train()](kernel/drivers/gpu/drm/bridge/analogix/analogix_dp_core.c#L776)

```
analogix_dp_fast_link_train()
├── analogix_dp_reset_macro()
├── 配置 TX: link_rate, lane_count, training_lane, enhanced_mode
├── 发送 TP1 → usleep(500us)
├── 发送 TP2 → usleep(500us)
├── 发送 DP_NONE (正常模式)
└── verify_fast_training (可选):
    ├── 读 DPCD link_status
    ├── clock_recovery_ok() 失败 → reduce_link_rate()
    └── channel_eq_ok() 失败   → reduce_link_rate()
```

Fast Training 的检测（决定是否可用）：
[analogix_dp_fast_link_train_detection()](kernel/drivers/gpu/drm/bridge/analogix/analogix_dp_core.c#L984)

```
读 DPCD: DP_MAX_DOWNSPREAD
  └── NO_AUX_HANDSHAKE_LINK_TRAINING bit → fast_train_enable
```

#### Full Link Training 状态机

[analogix_dp_full_link_train()](kernel/drivers/gpu/drm/bridge/analogix/analogix_dp_core.c#L700)

```
analogix_dp_full_link_train(max_lanes, max_rate)
│
├── 初始化: 读 DPCD → max bandwidth, max lane count, SSC
├── 裁剪: lane_count = min(sink_max, source_max)
│         link_rate   = min(sink_max, source_max)
├── lt_state = START
│
└── while(!finished):
    │
    ├── START:
    │   └── analogix_dp_link_start()    [analogix_dp_core.c#L354]
    │       ├── 设置 TX link_rate, lane_count
    │       ├── 写 DPCD: DP_LINK_BW_SET
    │       ├── 写 DPCD: DP_DOWNSPREAD_CTRL (展频 + 8b/10b)
    │       ├── analogix_dp_set_enhanced_mode()
    │       ├── training_lane[] = min voltage_swing + pre_emphasis
    │       ├── analogix_dp_set_training_pattern(TP1)
    │       └── 写 DPCD: DP_TRAINING_PATTERN_SET = TP1 + SCRAMBLING_DISABLE
    │       └── lt_state = CLOCK_RECOVERY
    │
    ├── CLOCK_RECOVERY:
    │   └── analogix_dp_process_clock_recovery()  [analogix_dp_core.c#L525]
    │       ├── usleep(100us)
    │       ├── 读 DPCD: DP_LANE0_1_STATUS, DP_ADJUST_REQUEST_LANE0_1
    │       ├── clock_recovery_ok() ?
    │       │   ├── YES: 选 TPS3(support) or TPS2
    │       │   │   ├── set_training_pattern(TPS2/TPS3)
    │       │   │   ├── 写 DPCD: DP_TRAINING_PATTERN_SET
    │       │   │   └── lt_state = EQUALIZER_TRAINING
    │       │   └── NO:
    │       │       ├── 每个 lane 检查 cr_loop
    │       │       ├── MAX_CR_LOOP(=5) or max swing → reduce_link_rate()
    │       │       └── 否则调整 voltage_swing & pre_emphasis
    │       │           └── 写 DPCD: DP_TRAINING_LANE0_SET
    │
    ├── EQUALIZER_TRAINING:
    │   └── analogix_dp_process_equalizer_training() [analogix_dp_core.c#L600]
    │       ├── usleep(400us)
    │       ├── 读 DPCD: DP_LANE0_1_STATUS, ADJUST_REQUEST, LANE_ALIGN_STATUS
    │       ├── !clock_recovery_ok() → reduce_link_rate() (CR 退化了)
    │       ├── !channel_eq_ok() → 成功!
    │       │   ├── training_pattern_dis()
    │       │   ├── 读回最终 link_rate, lane_count
    │       │   └── lt_state = FINISHED
    │       └── 否则:
    │           ├── eq_loop++, MAX_EQ_LOOP(=5) → reduce_link_rate()
    │           └── 写 DPCD: DP_TRAINING_LANE0_SET
    │
    ├── FINISHED: training_finished = 1
    └── FAILED:   return -EREMOTEIO
```

#### 降速机制

```
analogix_dp_reduce_link_rate()             [analogix_dp_core.c#L480]
├── analogix_dp_training_pattern_dis()     // 禁用训练图案
├── analogix_dp_set_enhanced_mode()        // 重新设置增强模式
└── lt_state = FAILED                      // 全链路训练失败
```

Note: Analogix DP 的降速与 CDN-DP 不同 —— CDN-DP 会循环尝试 `get_lower_link_rate()` 再重试，而 Analogix DP 降速后直接标记 FAILED。

### Link Status 检查与寄存器

#### CDN-DP 的关键寄存器

| 寄存器 | 地址 | 用途 |
|--------|------|------|
| `DP_FRAMER_GLOBAL_CONFIG` | 0x2200 | SST模式、lane数、NO_VIDEO(训练时)、GLOBAL_EN |
| `DP_TX_PHY_CONFIG_REG` | 0x2000 | 训练图案选择(TPS1/2/3/4)、scrambler/encoder bypass |
| `DPTX_LANE_EN` | 0x2300 | Lane 使能 (BIT(num_lanes)-1) |
| `DPTX_ENHNCD` | 0x2304 | Enhanced Framing 使能 |

#### Analogix DP 使用 DPCD 标准寄存器

| DPCD 地址 | 用途 |
|-----------|------|
| `DP_LINK_BW_SET` (0x0100) | 设置 link rate |
| `DP_LANE_COUNT_SET` (0x0101) | 设置 lane 数量 |
| `DP_TRAINING_PATTERN_SET` (0x0102) | 训练图案 + scrambling disable |
| `DP_TRAINING_LANE0_SET` (0x0103) | Lane 0/1 voltage swing + pre-emphasis |
| `DP_LANE0_1_STATUS` (0x0202) | CR_DONE, CHANNEL_EQ_DONE, SYMBOL_LOCKED |
| `DP_LANE_ALIGN_STATUS_UPDATED` (0x0204) |  Lane 对齐状态 |
| `DP_ADJUST_REQUEST_LANE0_1` (0x0206) | Sink 请求调整值 |

#### 状态检查宏

```
CR 完成: 每个 lane 的 CR_DONE bit (bit 0) 均置位
EQ 完成: 每个 lane 的 CHANNEL_EQ_BITS (bits 1:0) = 0x3
          + INTERLANE_ALIGN_DONE (bit 0 of LANE_ALIGN_STATUS)

CDN-DP:
  drm_dp_clock_recovery_ok()   → include/drm/drm_dp_helper.h
  drm_dp_channel_eq_ok()        → include/drm/drm_dp_helper.h

Analogix DP:
  analogix_dp_clock_recovery_ok()  [analogix_dp_core.c#L429]
  analogix_dp_channel_eq_ok()       [analogix_dp_core.c#L442]
```

### 训练结果对音频的影响

```
链路训练成功:
  ├── dp->link.rate       = 有效的 link rate (1.62/2.7/5.4 Gbps)
  ├── dp->link.num_lanes  = 有效的 lane 数 (1/2/4)
  ├── dp->active = true
  └── 音频可以开始配置和传输:
      ├── cdn_dp_audio_config() 中根据 link.num_lanes 计算 sub_pckt_num
      └── AUDIO_PACK_CONTROL |= AUDIO_PACK_EN

链路训练失败:
  ├── dp->active = false
  ├── dp->connected = false (触发 hotplug 事件断开)
  └── cdn_dp_audio_hw_params() → dp->active == false → 静默返回 0
```

## 二、热插拔 & EDID → ELD 链路

### 2.1 驱动加载 & 音频 Codec 注册

**CDN-DP 路径：**

1. [cdn_dp_probe()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1351) → 平台 probe
2. [cdn_dp_audio_codec_init()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1009) → `platform_device_register_data(dev, "hdmi-audio-codec", ...)` 注册音频 codec 平台设备
3. [audio_codec_ops](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1002) 提供回调：
   - `.hw_params = cdn_dp_audio_hw_params`
   - `.audio_shutdown = cdn_dp_audio_shutdown`
   - `.digital_mute = cdn_dp_audio_digital_mute`
   - `.get_eld = cdn_dp_audio_get_eld`

**Analogix DP 路径：**

1. [rockchip_dp_probe()](kernel/drivers/gpu/drm/rockchip/analogix_dp-rockchip.c#L593) → 平台 probe
2. [rockchip_dp_bind()](kernel/drivers/gpu/drm/rockchip/analogix_dp-rockchip.c#L498) → `platform_device_register_data(dev, "hdmi-audio-codec", ...)` (仅当 `data->audio == true`)
3. [rockchip_dp_audio_codec_ops](kernel/drivers/gpu/drm/rockchip/analogix_dp-rockchip.c#L126) 提供回调：
   - `.hw_params = rockchip_dp_audio_hw_params`
   - `.audio_startup = rockchip_dp_audio_startup`
   - `.audio_shutdown = rockchip_dp_audio_shutdown`
   - `.get_eld = rockchip_dp_audio_get_eld`

### 2.2 HDMI Codec 框架的 probe

[hdmi_codec_probe()](kernel/sound/soc/codecs/hdmi-codec.c#L849) → 解析 `hdmi_codec_pdata`，注册 I2S 和 SPDIF 两种 DAI：
- `"i2s-hifi"` — I2S 输入，最大 8 通道
- `"spdif-hifi"` — SPDIF 输入，固定 2 通道

### 2.3 HPD 插拔检测 → EDID 读取 → ELD 填充

**CDN-DP：**
1. [cdn_dp_pd_event()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1158) → EXTCON 通知回调
2. [schedule_work(&dp->event_work)](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1170) → 调度事件 work
3. [cdn_dp_pd_event_work()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1083) → 实际处理：
   - `cdn_dp_request_firmware()` → 加载 firmware
   - `cdn_dp_enable()` → 使能 DP 链路
   - `cdn_dp_get_sink_capability()` → 读取 DPCD + EDID
4. [cdn_dp_get_edid_block()](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L495) → 通过 mailbox 向 firmware 请求 EDID block
5. [cdn_dp_connector_get_modes()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L284)：
   - `drm_detect_monitor_audio(edid)` → 检测 sink 是否支持音频
   - `drm_connector_update_edid_property()` → 更新 connector->eld (EDID-Like-Data)

## 五、DP 音频 InfoFrame (SDP) 打包

DP 标准中音频通过 **Secondary Data Packet (SDP)** 传输 Audio InfoFrame。

[cdn_dp_setup_audio_infoframe()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L871)

## 九、热插拔重插时爆鸣声 & 无声问题分析

以下分析聚焦于**拔出后重新插入**（re-plug）场景——拔出的过程正常，问题出现在重新插入后，且概率性发生。

---

### 关键时间线：重插时 DP 硬件和 ALSA 的初始化顺序

```
HPD↑ → event_work → cdn_dp_enable():

  [A] cdn_dp_clk_enable()
      └── cdn_dp_clock_reset()
          └── SOURCE_AIF_CAR ← SPDIF_CDR_CLK_EN | AIF_SYS_CLK_EN | AIF_CLK_EN
              ↑ 音频输入接口时钟在此处使能！AIF 开始采样 I2S/SPDIF 引脚

  [B] cdn_dp_firmware_init()
      └── firmware 加载并激活

  [C] cdn_dp_enable_phy()
      └── PHY 上电

  [D] cdn_dp_get_sink_capability()
      └── EDID 读取, dp->sink_has_audio 确定

  [E] dp->active = true  ← ALSA hw_params 从此处起不再被短路
      dp->lanes = port->lanes

  ─── 但此时主链路尚未训练！link.rate / link.num_lanes 还是旧值或 0

DRM hotplug → 用户空间 → encoder enable:

  [F] cdn_dp_encoder_enable()
      ├── cdn_dp_enable() → dp->active 已为 true, 直接返回
      ├── cdn_dp_train_link()           ← 主链路训练!
      │   └── dp->link.rate, dp->link.num_lanes 可能改变
      └── cdn_dp_config_video()

  [G] ALSA open → hw_params → trigger    ← 可能发生在 [E]..[F] 之间或 [F] 之后
```

核心矛盾：**音频输入在 [A] 就活了，但音频处理流水线要到 [G] 才配置。而 [E] 到 [F] 之间 `dp->active=true` 但链路未训练。**

---

### 爆鸣声的三个根因

#### 根因 1：AIF 时钟先于音频通路配置使能 — 未配置的音频输入采样随机数据

[cdn_dp_clock_reset()](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L64-L70) 在 enable 的第一步就把音频接口时钟全开了：

```c
val = SPDIF_CDR_CLK_RSTN_EN | SPDIF_CDR_CLK_EN |
      SOURCE_AIF_SYS_RSTN_EN | SOURCE_AIF_SYS_CLK_EN |
      SOURCE_AIF_CLK_RSTN_EN | SOURCE_AIF_CLK_EN;
writel(val, dp->regs + SOURCE_AIF_CAR);
```

此时 DP 控制器内的 AIF（Audio Interface）已退出复位、时钟运行，开始采样外部 I2S/SPDIF 引脚上的信号。但下游的音频处理模块还处于未配置状态：

| 模块 | 状态 | 配置时机 |
|------|------|---------|
| AIF (音频接口) | **已使能** [A] | `clock_reset()` |
| AUDIO_SRC (解码器) | 复位/停止 | `audio_config()` [G] |
| SMPL2PKT (采样→包) | 复位/停止 | `audio_config()` [G] |
| FIFO | 复位 | `audio_config()` [G] |
| AUDIO_PACK_CONTROL | 禁用 | `audio_config()` [G] |

**如果此时 SoC 的 I2S/SPDIF TX 正在输出数据**（因为 jack 回调断裂，上轮播放的 CPU DAI 未被停止），AIF 会在 [A] 时刻开始采样到有效时钟边沿和数据，但下游通路是未初始化的。当 [G] 时刻 `AUDIO_SRC_CNTL` 写入 `I2S_DEC_START` 或 `SPDIF_CTRL_ADDR` 使能 SPDIF 时，解码器从**一个随机的比特位置**开始对齐帧——第一个采样窗口几乎必然是垃圾。这份垃圾数据通过 SMPL2PKT 打包、经 `AUDIO_PACK_EN` 使能后作为第一个音频包发出 → **爆鸣**。

**概率性**：取决于重插瞬间 I2S/SPDIF TX 是否在跑、以及 AIF 采样时钟与数据线的相位关系。

---

#### 根因 2：`dp->active` 在链路训练前置 true — ALSA 可能在未训练链路上配置音频

[cdn_dp_enable()](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L606) 在**链路训练之前**就设了 `dp->active = true`：

```
cdn_dp_enable():                          cdn_dp_encoder_enable():
  ...                                       cdn_dp_enable() → 已 active, 跳过
  dp->active = true  ← [E]                  cdn_dp_train_link()  ← [F] 才训练!
  return 0;                                 dp->link.rate  = 训练结果
                                            dp->link.num_lanes = 训练结果
```

[E] 到 [F] 之间有一段时间窗口：`dp->active=true`，但 `dp->link.rate` 和 `dp->link.num_lanes` 可能是 0（刚 reset）或上一次的值。如果 [G]（ALSA hw_params）恰好落在此窗口：

- [cdn_dp_audio_config()](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L1046) 中的 `sub_pckt_num` 会基于当前 `dp->link.num_lanes` 计算
- 如果此时 `num_lanes` 是 0（reset 值），`sub_pckt_num` 计算错误 → 音频包时序不对
- 如果此时 `num_lanes` 是旧值，后续训练可能改变它 → 音频配置基于过期参数

这形成了竞态：`sub_pckt_num` 的正确值在 [F] 才确定，但 ALSA 可能在 [E] 就开始配置了。

**概率性**：取决于 ALSA 用户空间对 HPD 事件的响应速度 vs DRM atomic commit 的完成速度。

---

#### 根因 3：硬件 reset 后 ALSA 不重配 — 旧 stream 在新硬件上继续跑

拔出后 `cdn_dp_disable()` 将硬件完全复位（firmware 关、时钟关、寄存器丢失）。重插后 `cdn_dp_enable()` 重建硬件，所有寄存器回到 reset 默认值。

但如果 jack 回调断裂（[audio_codec_ops](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1002) 缺少 `.hook_plugged_cb`），PulseAudio 不知道发生过插拔——PCM 从未关闭、`hw_params` 不会再调、`audio_config()` 不会再执行。

结果：**硬件是新的（全 0），ALSA 以为配置还在** → 音频数据通过 I2S/SPDIF 持续灌入，但 DP 控制器内的 AUDIO_SRC_CNTL=0（解码器不工作）、AUDIO_PACK_CONTROL=0（不发包）→ **无声**。如果此时 ALSA 恰好调 `digital_mute(false)`（取消静音），且 `dp->active=true`，mute 操作通过了，但音频通路实际上从未被配置 → 用户听到的可能是硬件随机状态下的杂音。

**概率性**：取决于 PulseAudio 是否恰好在插拔间隙关闭了 PCM（如果 udev 触发了 sink 移除则不会，如果没触发则会）。

---

### 无声的两个额外根因

#### 根因 4：`hw_params` 在 `!dp->active` 时返回 0

同上一节分析。PulseAudio 在 [E] 之前调 `hw_params` → 返回 0 → 认为配置成功 → 实际上寄存器未写入。

#### 根因 5：Link 重训练后音频配置不跟随更新

同上一节分析。`sub_pckt_num` 依赖 `num_lanes`，重训练改变 lane 数后只重配视频不重配音频。

---

### 泛化：七条设计原则 —— 保证任何情况下不出现爆鸣或无声

以上所有根因最终可以归结为七条原则的违反。这七条原则适用于任何 "音频硬件寄生在热插拔链路上、由两个子系统分治" 的架构（DP/HDMI/USB Audio）。

---

#### 原则 1：断电/复位前必须先停音频 (Teardown Ordering)

> **音频输出路径的每一级（packetizer → FIFO → 解码器 → 输入时钟）必须在依赖它的硬件被移除前按逆序停止。**

类比：拔电源之前先关机，而不是直接拉闸。

**违反后果**：如果 Firmware、core clock、PHY 等被先关掉，音频 packetizer 失能瞬间输出线可能产生毛刺 → 爆鸣。

**对本例的要求**：[`cdn_dp_disable()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L537) 的第一步必须是 `cdn_dp_audio_stop()`。当前代码完全没有调用它。

**验证方式**：在 disable/suspend/remove 函数中加断言——如果 `audio_info.format != AFMT_UNUSED`（说明音频未停），则 WARN 并强制执行 audio_stop。

---

#### 原则 2：音频输入时钟不得早于音频通路配置使能 (Late Input Clock)

> **音频输入接口（AIF）的时钟/复位，必须在 FIFO + 解码器 + Packetizer 全部配置完毕后才释放。在通路未就绪时，不能让输入开始采样。**

类比：先把水管接好，再开水龙头。不是先开水龙头再接水管。

**违反后果**：[`cdn_dp_clock_reset()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L64-L70) 在 enable 第一步就开了 AIF 时钟。此时外部 I2S/SPDIF 可能正在翻转，未初始化的解码器从随机相位锁定 → 第一帧是垃圾 → 爆鸣。

**对本例的要求**：`SOURCE_AIF_CAR` 的写操作应从 `clock_reset()` 移到 `cdn_dp_audio_config()` 中，在 AUDIO_SRC_CNTL 配置完毕后执行。或者至少，在 `clock_reset()` 中使能 AIF 时钟后，立即写 `AUDIO_SW_RST` 保持解码器和 packetizer 在复位状态，直到 `audio_config()` 才释放。

**验证方式**：在 AIF 时钟使能和 audio_config 之间插入 check：读 `AUDIO_SRC_CNTL`，如果值为 0 且 AIF 时钟已开 → 报错。

---

#### 原则 3：Mute 和清理操作是硬操作，不依赖软件状态标志 (Unconditional Side Effects)

> **digital_mute 的本质是写一个寄存器 bit 让它静音。audio_shutdown 的本质是清 FIFO、关时钟、关 packetizer。这些操作的存在意义就是做清理——它们必须在任何软件状态下都能执行。**

类比：灭火器的使用不依赖于"是否在火灾演练期间"。它就是用来灭火的，无论什么状态下都能喷。

**违反后果**：[`cdn_dp_audio_digital_mute()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L980) 和 [`cdn_dp_audio_shutdown()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L963) 都在 `!dp->active` 时跳过实际操作。当 DRM 先关了硬件、ALSA 后到做清理时，清理被短路 → mute 无效、FIFO 未清 → 爆鸣。

**对本例的要求**：这两个函数移除 `if (!dp->active)` 守卫。硬件寄存器写操作本身不依赖 DP 链路是否 active——`DP_VB_ID` 寄存器在时钟使能时就可写，AUDIO_SRC_CNTL 的复位也是本地操作。

**通用区分标准**：

| 操作类型 | 是否依赖 active | 示例 |
|---------|---------------|------|
| 查询类（读 sink 状态） | 是 | `get_eld`, `get_hpd_status` |
| 配置类（写本地寄存器） | 否 | `digital_mute`, `audio_stop`, `audio_config` |

---

#### 原则 4：硬件复位后必须无条件重配音频 (Re-init → Re-config)

> **如果音频硬件寄存器因 reset/power-cycle 丢失，所有依赖这些寄存器的软件层必须被通知并重新配置。无论 ALSA stream 当前处于什么状态。**

类比：BIOS 重置后，操作系统不会假设上次的配置还在——它会重新初始化所有硬件。

**违反后果**：HPD 重插 → `cdn_dp_enable()` reset 硬件 → 所有音频寄存器回到默认值（全 0）。但 PulseAudio 不知道硬件 reset 了（jack 回调断裂），不重调 `hw_params` → AUDIO_SRC_CNTL=0, AUDIO_PACK_CONTROL=0 → 无声。

**对本例的要求**：实现 [`hook_plugged_cb`](kernel/include/sound/hdmi-codec.h#L114)，使 DRM 的 HPD 事件能触发 `plugged_cb` → `hdmi_codec_jack_report()` → ALSA jack 通知。收到 jack 插入事件后，ALSA 用户空间会重新 open + hw_params。同时，`hw_params` 必须可重入——调用第二次时能正确覆盖第一次的寄存器配置。

**验证方式**：用 ftrace 埋点确认完整调用链：`cdn_dp_pd_event → plugged_cb → hdmi_codec_jack_report → snd_soc_jack_report → userspace udev → PipeWire reconnect → ALSA hw_params → cdn_dp_audio_config`。链上任一环节缺失即 bug。

---

#### 原则 5：就绪标志必须在所有依赖参数确定后置位 (Truthful Readiness)

> **任何门控音频操作的"就绪"标志（如 `dp->active`），必须在其依赖的所有硬件参数都已最终确定、不会再变之后，才置为 true。**

类比：餐厅告诉客人"可以点餐了"时，厨房、厨师、食材必须全部到位。不能说"门开了就算可以点餐"。

**违反后果**：[`cdn_dp_enable()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L606) 在 link training 之前就设了 `dp->active = true`。此时 `dp->link.rate` 和 `dp->link.num_lanes` 尚未确定（可能是 0）。ALSA `hw_params` 在此窗口调用 → `sub_pckt_num` 基于无效值计算 → 音频包时序错误。

**对本例的要求**：`dp->active = true` 应移到 [`cdn_dp_encoder_enable()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L664) 中，在 `cdn_dp_train_link()` 和 `cdn_dp_config_video()` 都成功之后才置位。或者拆成两个标志：`dp->clocks_ready`（AIF 可配置）和 `dp->link_ready`（音频可发包），`hw_params` 只依赖前者，`AUDIO_PACK_EN` 只依赖后者。

---

#### 原则 6：事件传播链路的每一环都必须实现 (Complete Event Chain)

> **硬件事件（HPD、link loss、reset）需要通知到做决策的软件层（ALSA 用户空间）时，传播链路上的每一个 callback、每一个 notifier、每一个函数指针都必须被实现。不存在"可选"的中间环。**

类比：消防报警链——探测器→控制面板→警铃→消防队。任何一环"可选"意味着警报传不到。

**违反后果**：[`audio_codec_ops`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1002) 没有 `.hook_plugged_cb` → `hdmi_codec_set_jack()` 返回 `-EOPNOTSUPP` → `plugged_cb` 从未注册 → ALSA 用户空间收到 0 个 jack 事件 → PipeWire 不知道设备拔了或重插了。

**对本例的要求**：

```
传播链（必须每一环都实现）：

DRM HPD event
  → cdn_dp_pd_event_work()
    → hdmi_codec_ops.hook_plugged_cb()     ← 当前缺失
      → hdmi_codec plugged_cb()             [hdmi-codec.c#L766]
        → hdmi_codec_jack_report()          [hdmi-codec.c#L757]
          → snd_soc_jack_report()           [sound/soc/soc-jack.c]
            → ALSA core jack event
              → udev → PipeWire/PulseAudio → 重开 PCM 或关闭 PCM
```

**验证方式**：`echo 1 > /sys/kernel/debug/tracing/events/snd_soc_jack/enable`，插拔 DP 线，确认 `snd_soc_jack_report` 被调用。

---

#### 原则 7：链路参数变化时音频配置必须跟随更新 (Configuration Follows Parameters)

> **当链路参数（rate、lanes）在运行时改变，所有依赖于这些参数的音频配置（sub_pckt_num、N/CTS、InfoFrame）必须同步刷新。不允许只更新视频不更新音频。**

类比：公路从 4 车道缩减为 2 车道时，公交专用道的调度时刻表必须重算，不能只更新私家车道。

**违反后果**：[`cdn_dp_pd_event_work()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1137) 在重训练后只调了 `cdn_dp_config_video()`，没调 `cdn_dp_audio_config()`。lane 数变化 → `sub_pckt_num` 错 → 音频包在主链路上的时序错。对 1-lane 链路，`sub_pckt_num` 是 2；对 2/4-lane 是 4。错了意味着每 MTP 发送的音频包数量不对 → sink 解码失败 → 无声或噪声。

**对本例的要求**：`cdn_dp_pd_event_work()` 的重训练分支中，在 rate/lanes 变化时增加对 `cdn_dp_audio_config()` 和 `cdn_dp_setup_audio_infoframe()` 的调用。更通用的设计是把 `config_video` + `config_audio` + `setup_infoframe` 合并为一个 `reconfigure_link()` 函数，每次链路参数变化时统一调用，确保不会有遗漏。

---

### 七条原则之间的关系

```
         ┌──────────────────────────────┐
         │  硬件状态改变 (HPD / Reset)    │
         └──────────────┬───────────────┘
                        │
         ┌──────────────▼───────────────┐
         │  原则 6: 事件通知 ALSA        │  ← 确保 ALSA 知道发生了什么
         └──────────────┬───────────────┘
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
┌─────────────────────┐   ┌─────────────────────┐
│  链路断开 (unplug)   │   │  链路建立 (plug)     │
├─────────────────────┤   ├─────────────────────┤
│ 原则 1: 先停音频再关 │   │ 原则 2: 通路就绪后才  │
│        硬件 (顺序)   │   │        开输入时钟     │
│ 原则 3: mute 无条件 │   │ 原则 4: 硬件复位后    │
│        (不被短路)    │   │        无条件重配     │
│                     │   │ 原则 5: 参数确定后才   │
│                     │   │        宣布就绪       │
│                     │   │ 原则 7: 参数变化时     │
│                     │   │        跟随刷新       │
└─────────────────────┘   └─────────────────────┘
```

原则 6 是**信息通道**——确保链路事件到达决策层。其余六条是**行为规范**——三条针对断开路径、三条针对建立路径。原则 3 跨两条路径：断开时 mute、初始化时保持 mute 直到配置完成。
