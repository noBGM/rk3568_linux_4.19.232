# 自研 SoC 平台 Command Mode → Video Mode 切换评估框架

> 通用方法论，独立于具体芯片平台。以"评估者"视角，分硬件、软件、系统集成三个层次。

---

## 1. 硬件可行性

| 评估项 | 要确认什么 | 怎么确认 | 不满足时的后果 |
|--------|----------|---------|-------------|
| **Panel 双模支持** | Panel IC 的数据手册是否同时列出 Command Mode 和 Video Mode 两套寄存器配置序列 | 找 Panel 原厂要完整的 initialization sequence，确认其中存在 Video Mode 专用的 DCS 写寄存器步骤 | 致命 — Panel 硬件不支持则无法继续 |
| **Panel GRAM bypass** | Command Mode 依赖 Panel 内部 GRAM，Video Mode 下像素流是否绕过 GRAM 直接驱动列驱动器 | 查 Panel IC 规格书中 "Video Mode data path" 框图 | 高 — 部分 Panel GRAM 不能 bypass，Video Mode 下画面会错乱 |
| **DSI PHY 速率上限** | `lane_rate = htotal × vtotal × bpp × fps / lanes` 是否 ≤ PHY 最大速率 | 计算所需 bandwidth，对比 SoC 数据手册中 DSI PHY 的 `max_data_rate_per_lane` | 致命 — 超速则链路训练失败，无画面 |
| **DSI PHY HS/LP 切换** | Video Mode 下消隐期需要频繁 HS↔LP 切换，PHY 是否满足时序 | 查 SoC PHY 的 THS-SETTLE / TLPX / TCLK-PREPARE 等参数是否在 DSI Spec 范围内 | 中 — 时序不满足会导致 bit error 或 Panel 侧误判 |
| **TE 引脚处理** | Command Mode 依赖 TE GPIO 做帧同步，Video Mode 下此引脚是否可复用为普通 GPIO 或悬空 | 查 SoC pinmux 表，确认 TE 引脚的状态 | 低 — 即使未处理，软件忽略 TE 中断即可 |
| **显示控制器输出能力** | Video Mode 下 Display Controller 需持续输出像素流而非按需触发，内部 FIFO/DMA 是否支撑 | 查 SoC Display Controller 的最大分辨率/帧率，以及是否存在 "streaming mode" 与 "trigger mode" 的区分 | 高 — 带宽不足会导致 underrun(画面撕裂) |
| **时钟架构** | Video Mode 需要稳定的像素时钟持续输出，Command Mode 可能在空闲时门控时钟 | 确认 SoC 的时钟树中 DSI pixel clock 和 D-PHY HS clock 的来源和门控逻辑 | 中 — 时钟门控不当会导致 PHY 失锁 |

## 2. 前置概念：所谓"驱动已有完整 Video Mode 代码"指两个驱动

评估中多次提到的"驱动是否已有 Video Mode 代码"，特指以下**两个独立驱动**：

```
┌──────────────────────────────────────────────────┐
│  驱动一：DSI Host Controller 驱动                 │
│  ──────────────────────────────────────────────  │
│  负责 MIPI DSI 协议层的硬件配置                    │
│                                                   │
│  需要的函数：                                      │
│  ├── encoder_enable()                             │
│  │     ├── lane 速率计算                          │
│  │     ├── DPI 颜色编码 (16/18/24bit)             │
│  │     ├── HSYNC/VSYNC 极性                      │
│  │     └── if (mode_flags & VIDEO)                │
│  │           set_vid_mode()  ← 核心！             │
│  │         else                                   │
│  │           set_cmd_mode()                       │
│  │                                                │
│  ├── set_vid_mode()          ← 这个函数必须存在   │
│  │     ├── DSI_VID_MODE_CFG  ← 消隐区 LP/HFP      │
│  │     ├── DSI_VID_PKT_SIZE  ← 每行像素数         │
│  │     ├── DSI_VID_HTIME     ← 水平时序 (HSA/HBP) │
│  │     ├── DSI_VID_VTIME     ← 垂直时序 (VSA/VBP) │
│  │     └── DSI_MODE_CFG      ← 切 VID (bit0→0)    │
│  │                                                │
│  ├── set_cmd_mode()          ← 安全回落（可选）    │
│  └── disable() / pre_enable()  ← 状态机完整性      │
│                                                   │
│  对应芯片实例：                                    │
│    Rockchip: dw-mipi-dsi.c                        │
│    Synopsys:  bridge/synopsys/dw-mipi-dsi.c       │
│    Qualcomm:  msm/dsi/dsi_host.c                  │
│    Mediatek:  mediatek/mtk_dsi.c                  │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│  驱动二：Display Controller 驱动（CRTC）          │
│  ──────────────────────────────────────────────  │
│  负责 SoC 内部显示控制器的硬件配置                 │
│                                                   │
│  需要的函数：                                      │
│  ├── crtc_atomic_enable()                         │
│  │     ├── 从 drm_display_mode 提取 timing:       │
│  │     │     htotal, hact_st/end, hsync_len       │
│  │     │     vtotal, vact_st/end, vsync_len       │
│  │     ├── 写 timing 寄存器:                      │
│  │     │     HTOTAL_PW / HACT_ST_END              │
│  │     │     VTOTAL_PW / VACT_ST_END              │
│  │     ├── VOP_MODULE_SET(out_mode)  ← 输出格式    │
│  │     ├── 使能 MIPI 输出 (mipi_en)               │
│  │     ├── VP → MIPI 路由 (mipi_mux)              │
│  │     ├── clk_set_rate(dclk)    ← 像素时钟       │
│  │     └── cfg_done()            ← 寄存器锁存      │
│  │                                                │
│  ├── crtc_atomic_flush()                          │
│  │     ├── cfg_update()  ← overlay/背景/BCSH      │
│  │     └── cfg_done()    ← 帧同步                 │
│  │                                                │
│  └── crtc_atomic_disable()                        │
│        └── standby()       ← 停止输出             │
│                                                   │
│  对应芯片实例：                                    │
│    Rockchip: rockchip_drm_vop2.c                  │
│    Qualcomm: msm/disp/dpu1/dpu_crtc.c             │
│    Mediatek: mediatek/mtk_drm_crtc.c              │
└──────────────────────────────────────────────────┘
```

**两个驱动缺一不可**。如果 DSI Host 驱动有 `set_vid_mode()` 但 Display Controller 不支持 streaming 持续输出，像素数据根本送不到 DSI 接口；反过来 Display Controller 配好了 timing 但 DSI Host 还卡在 Command Mode，Panel 收不到正确的 DPI 视频流。

## 3. 软件改动量

| 软件模块 | 改动内容 | 评估方法 | 参考工作量 |
|---------|---------|---------|-----------|
| **Panel 驱动** | `mode_flags` 添加 `MIPI_DSI_MODE_VIDEO`（以及子模式 BURST/SYNC_PULSE/SYNC_EVENT） | 对比现有 CMD Mode 的 panel 驱动，确认是否只需改 `mipi_dsi_device` 的标志位 | 0.5 天 |
| **Panel DCS 序列** | Command Mode 和 Video Mode 的 Panel 初始化 DCS 命令序列完全不同，需重写 | 从 Panel 原厂获取 Video Mode Application Note，逐条对比两套序列的差异点 | 1-3 天 |
| **DSI Host 驱动** | 修改 `DSI_MODE_CFG` 寄存器（bit 0 → 0），配置 video timing 寄存器组 | 如果 DSI Host 驱动没有实现 `set_vid_mode()`，需从头编写；如果已有，确认状态机是否完整覆盖 disable→pre_enable→enable 全路径 | 已有: 0 天；无: 3-5 天 |
| **DSI Host 中断处理** | Video Mode 不再需要 TE 中断，但需要 VSYNC/VBLANK/underrun 中断 | 确认 DSI Host 驱动和 Display Controller 驱动的中断注册/处理链路 | 0.5-1 天 |
| **Display Controller 驱动** | Video Mode 下需配置完整的 porches 时序（HFP/HBP/HSA/VFP/VBP/VSA），Command Mode 可能省略 | 确认 Display Controller 的 timing 寄存器是否支持该分辨率，且与 Panel 的 porch 参数匹配 | 0.5-1 天 |
| **Display Controller 输出模式** | 确认输出接口的 bus_format / output_mode 寄存器与 Video Mode 的 DSI 数据包格式一致 | 确认 `output_mode`(如 P888/P666/P565) 和 DSI `DPI_COLOR_CODING` 的一致性 | 0.5 天 |
| **Device Tree** | 修改 Panel 节点中的 `dsi,flags`、添加必要的 timing 参数 | 对比 CMD/VID 两模式的 DTS 差异 | 0.5 天 |
| **Bootloader** | 部分平台的 Bootloader 也会初始化 DSI 显示 Logo，需同步修改 | 查 Bootloader 是否使用同一 Panel，如是则同步修改 | 0-1 天 |

## 4. 平台特定风险

| 风险点 | 为什么是风险 | 评估手段 |
|--------|------------|---------|
| **DSI IP 版本** | 不同版本的 Synopsys/SNPS DSI IP 对 Video Mode 支持程度不同（如 HWVER_131 的 PHY timing 配置方式不同） | 读 `DSI_VERSION` 寄存器，对照 IP 版本的 release note |
| **显示控制器的 streaming vs trigger 模式** | 有些 SoC 的 Display Controller 只为 Command Mode 设计（按需触发），加 Video Mode 需要 DMA 持续搬运，触发系统总线带宽瓶颈 | 跑最大分辨率下的系统总线负载仿真 |
| **MCU/DBI 接口残留** | CMD Mode 使用 DBI(MCU) 接口，寄存器中可能有遗留配置干扰 DPI(Video) 数据路径 | 检查 Display Controller 中 MCU 相关寄存器的复位值和当前值 |
| **DVFS 耦合** | Command Mode 空闲时 SoC 降频，Video Mode 持续输出使系统无法进入深度睡眠 | 实测 Video Mode 持续点亮下的 SoC 功耗和温度 |
| **非连续时钟** | CMD Mode 常用 `MIPI_DSI_CLOCK_NON_CONTINUOUS`（clock lane HS 按需开启），Video Mode 下部分 Panel 只支持连续时钟 | 与 Panel 原厂确认 clock lane 要求 |

---

## 5. 风险评估 — 按严重程度

| 等级 | 条件 | 例子 |
|------|------|------|
| **致命 (Blocker)** | Panel 硬件不支持 Video Mode，或 DSI PHY 速率不够 | Panel 只有 GRAM 读路径无 bypass，或分辨率超过 PHY 物理上限 |
| **高** | 需要大量软件从零开发 | DSI Host 驱动缺 `set_vid_mode()` 且 Display Controller 驱动无 streaming mode 支持 |
| **中** | 软件已部分支持但未经验证 | 代码已写但从未在 Video Mode Panel 上实测过 |
| **低** | 纯配置级改动 | 只有 DTS 和 `mode_flags` 需要改，所有驱动已有完整支持 |

## 6. 工期估算公式

```
总工期 = P_ds × (T_panel + T_dsi + T_dc + T_dts + T_boot + T_test)
          └─ 并行系数(0.6-1.0)   └─ 各项串行/并行任务
```

### 各任务典型工期（通用估计）

| 任务 | 最小(已有代码) | 最大(从零开发) | 取决于 |
|------|-------------|-------------|--------|
| T_panel — Panel 驱动 + init sequence | 1 天 | 5 天 | Panel 原厂支持力度 |
| T_dsi — DSI Host 驱动 | 0 天 | 5 天 | 驱动中 Video Mode 代码是否已存在 |
| T_dc — Display Controller 驱动 | 0.5 天 | 3 天 | streaming mode 支持程度 |
| T_dts — Device Tree | 0.5 天 | 1 天 | — |
| T_boot — Bootloader 同步 | 0 天 | 1 天 | 是否需要显示 Logo |
| T_test — 测试验证 | 2 天 | 5 天 | 问题复杂度 |

### 场景估算

| 场景 | 条件 | 估算工期 |
|------|------|---------|
| **最优** | Panel 支持 VID + 驱动已有完整 Video Mode 代码 | **3-5 人日** |
| **典型** | Panel 支持 VID + 驱动缺 Video Mode 代码但 DSI IP 支持 | **8-15 人日** |
| **最差** | Panel 支持 VID + DSI IP 不支持 Video Mode + Display Controller 不支持 streaming | **不可行，需重新设计硬件** |
