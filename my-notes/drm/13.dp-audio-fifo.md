# DP 音频 FIFO 溢出：为什么热插拔重插后会爆鸣或无声

## 一、先理解数据怎么流的

```
SoC I2S/SPDIF 控制器          CDN-DP 控制器内部                  DP Main Link
(CPU DAI)                                                     → 显示器
     │                            │                               │
     │  BCK + LRCK + DATA         │                               │
     ├───────────────────────────▶│                               │
     │                            ├─ AIF (音频接口)                │
     │                            │   └─ 采样 I2S/SPDIF 引脚      │
     │                            ├─ AUDIO_SRC (解码器)            │
     │                            │   └─ I2S/SPDIF → 内部 PCM     │
     │                            ├─ SMPL2PKT (采样→包)            │
     │                            │   └─ PCM 样本 → DP 音频包     │
     │                            ├─ FIFO (缓冲)   ← 本文主角     │
     │                            │   └─ 环形缓冲区               │
     │                            ├─ Packetizer (打包器)           │
     │                            │   └─ 音频 SDP → Main Link     │
     │                            │                               ├──▶
     │                            │                               │
```

音频数据从左到右流动。FIFO 夹在"采样→包"和"打包器"之间，是一个环形缓冲区。

**关键**：左侧的 I2S/SPDIF 控制器和右侧的 CDN-DP 控制器是**两个独立的硬件模块**，各自有自己的时钟域和复位域。它们之间没有硬件流控——I2S TX 只管往外发，CDN-DP 的 AIF 只管往里收，谁也不会说"等一下，满了"。

---

## 二、FIFO 怎么被操作

整个驱动对 FIFO（寄存器 `FIFO_CNTL`，地址 `0x30088`）只有三种操作：

```
FIFO_CNTL 寄存器的两个控制位:

  BIT(0): AUDIO_SW_RST      — 软件复位，同时复位读写指针，清空 FIFO
  BIT(1): SYNC_WR_TO_CH_ZERO — 把写指针对齐到通道 0 的起始边界（只调 W，不动 R）
```

| 操作 | 在哪里调用 | 做了什么 |
|------|----------|---------|
| `AUDIO_SW_RST` | [`cdn_dp_audio_stop()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L895) | 复位 FIFO，**双指针归零** |
| `SYNC_WR_TO_CH_ZERO` | [`cdn_dp_audio_config_i2s()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L934) | **只对齐 W 到通道边界**，不动 R |
| `SYNC_WR_TO_CH_ZERO` | [`cdn_dp_audio_config_spdif()`](kernel/drivers/gpu/drm/rockchip/cdn-dp-reg.c#L1013) | 同上 |

### SYNC_WR_TO_CH_ZERO 到底做了什么

先看 I2S 总线上立体声音频数据的排列：

```
时间 →

LRCK:  ─┐         ┌─────────┐         ┌─────────
        │  左声道   │  右声道   │  左声道   │  右声道
        └─────────┘         └─────────┘

DATA:  ...L0... ...R0... ...L1... ...R1... ...L2... ...R2...
         ↑        ↑        ↑        ↑        ↑        ↑
       通道0    通道1    通道0    通道1    通道0    通道1
```

AIF 每采到一个数据字，就往 FIFO 里写一个 entry，W 前进一格。**通道 0 总是落在偶数位置，通道 1 总是在奇数位置**：

```
FIFO 地址:
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│  0  │  1  │  2  │  3  │  4  │  5  │  6  │  7  │ ...
├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
│ L0  │ R0  │ L1  │ R1  │ L2  │ R2  │ L3  │ R3  │ ...
└─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
  ↑                       ↑
 偶数地址 = 通道0 (左)    偶数地址 = 通道0 (左)
```

如果 W 停在奇数地址，下一个采样被写入奇数位置，读出时会被当成右声道——**左右颠倒**。`SYNC_WR_TO_CH_ZERO` 就是防止这个：把 W 挪到下一个偶数地址边界。

```
没有 SYNC，W 停在了 R1 之后:       有 SYNC，W 被强制对齐到 L2:

  W 在地址 4 (已经是偶数，但假设           W 被挪到最近的偶数地址
  它在 R1 之后):                           边界:

   ... R0  L1  R1  L2  R2 ...             ... R0  L1  R1  L2  R2 ...
              ↑                                       ↑
         W 恰好是偶数，                   W 确保下一个写入是 L
         下一个是 L2，没问题

但如果 W 在地址 3 (奇数):

   ... R0  L1  R1  ??  ?? ...    →    ... R0  L1  R1  L2  R2 ...
              ↑                                  ↑
         下一个写入在奇数                    W 跳到地址 4
         L2 被当成 R1 处理                  L2 正确写入偶数地址
```

### SYNC 和 AUDIO_SW_RST 的能力对比

```
SYNC_WR_TO_CH_ZERO (BIT 1):         AUDIO_SW_RST (BIT 0):

  W 对齐到通道边界   ✓                W = 0              ✓
  W 归零             ✗                R = 0              ✓
  R 被改动           ✗                FIFO 内容清空      ✓
  FIFO 内容清空      ✗                环形的"圈数"重置   ✓
  环形的"圈数"重置   ✗
```

用一句话总结：

> **`SYNC` 只调整了 W 的"相位"（对齐通道 0），不动 W 的"圈数"。`AUDIO_SW_RST` 把圈数和相位全归零。**

### 这意味着什么

`audio_config()` 只调了 `SYNC` 没调 `AUDIO_SW_RST`。如果 W 已经在配置前绕了 43 圈，SYNC 只是在第 43 圈的某个通道 0 边界上把 W 对齐了一下。**W 和 R 的相对关系毫无改变**——R 仍然停在 `cdn_dp_disable()` 切时钟的那个瞬间，W 仍然领先 R 几十圈。

```
SYNC 之后:

  R (断电瞬间的位置)                W (被 SYNC 对齐到通道边界)
       ↓                                       ↓
  ┌─────┬─────┬ ... ┬─────┬─────┬─────┬ ... ┬─────┐
  │ ??? │ ??? │     │ A2  │ A3  │ A4  │     │ A57 │
  └─────┴─────┴ ... ┴─────┴─────┴─────┴ ... ┴─────┘
       ↑                                       ↑
  读出来的第一帧                             刚写入的
  不知道是什么                               也不知道是不是从通道0开始

  SYNC 做的事: W 对齐到通道边界 ✓
  没做的事: R 位置调整 ✗, FIFO 清空 ✗, W 绕圈数归零 ✗
```

**问题已经浮现了**：`audio_config()` 只写 `SYNC_WR_TO_CH_ZERO`，不写 `AUDIO_SW_RST`。它假定 FIFO 在配置前读写指针处于合理位置。重插场景下，R 指向上次断电瞬间的随机地址，W 已经绕了几十圈——这个假设不成立。

## 三、重插时到底发生了什么

### 前提

PulseAudio/PipeWire 不知道 DP 被拔出了，因为 jack 回调断裂（[`audio_codec_ops`](kernel/drivers/gpu/drm/rockchip/cdn-dp-core.c#L1002) 缺少 `.hook_plugged_cb`）。PCM 流从未关闭，**SoC 的 I2S/SPDIF TX 一直在引脚上推数据**。

### 时间线

```
拔出 (T = -2s):
  HPD↓ → cdn_dp_disable()
  ├── firmware 关
  ├── 时钟全关 (AIF 也关了)
  └── dp->active = false

  但 I2S TX 引脚还在翻转 (PulseAudio 没停)

──────────────────── 若干秒后，重新插入 ────────────────────

重插 (T = 0):
  HPD↑ → event_work → cdn_dp_enable()

T = 0ms:
  cdn_dp_clk_enable()
    └── cdn_dp_clock_reset()
        └── writel(SOURCE_AIF_CAR, SPDIF_CDR_CLK_EN | AIF_SYS_CLK_EN | AIF_CLK_EN)
            ↑
            AIF 时钟活了！音频接口开始采样 I2S 引脚！
            但 FIFO 下游全部还在复位/未配置状态。
            读指针 R 停在 cdn_dp_disable() 断电前的随机位置。

  ┌─────────────────────────────────────────┐
  │  FIFO 状态:  写指针 W 开始从 0 累加      │
  │              读指针 R = 某个随机值        │
  │              AUDIO_PACK_EN = 0 (不发包)   │
  │              SMPL2PKT_EN  = 0 (不读FIFO) │
  └─────────────────────────────────────────┘

T = 0.1ms ~ 150ms:
  Firmware 加载 + PHY 上电 + EDID 读取
  I2S 数据持续灌入 FIFO，W 不断累加、回绕

  数据率: 48kHz × 2ch × 24bit = 2.304 Mbps = 288 KB/s
  假设 FIFO 深度 1KB: 填满一次 ≈ 3.5ms
  W 在 150ms 内绕了 150÷3.5 ≈ 43 圈

  ┌─────────────────────────────────────────┐
  │  W 已经绕了 43 圈                          │
  │  R 还是那个随机值                          │
  │  FIFO 里是 43 轮覆盖后的"当前"数据          │
  └─────────────────────────────────────────┘

T = 150ms:
  dp->active = true  ← ALSA 现在可以调 hw_params 了

T = ~200ms (取决于用户空间响应速度):
  ALSA hw_params → cdn_dp_audio_config_i2s()

  cdn_dp_audio_config_i2s() 执行:
    ① writel(SYNC_WR_TO_CH_ZERO, FIFO_CNTL)  // W 对齐到通道 0 边界
    ② 配置采样宽度、通道数、采样率...
    ③ writel(SMPL2PKT_EN, SMPL2PKT_CNTL)     // 采样→包 开始读 FIFO!
    ④ writel(I2S_DEC_START, AUDIO_SRC_CNTL)   // 解码器启动

  cdn_dp_reg_write(AUDIO_PACK_CONTROL, AUDIO_PACK_EN)  // 音频包开始上链

  ┌─────────────────────────────────────────┐
  │  写入: W 指向当前 I2S 数据的最新位置       │
  │  读出: R 仍指向断电前的位置 (从未复位过)    │
  │                                         │
  │  如果 R 恰好 ≈ W:  数据正确 → 正常        │
  │  如果 R 远 < W:    读到过期数据 → 爆鸣     │
  │  如果 R > W:       读到空白区(0) → 无声    │
  └─────────────────────────────────────────┘
```

### 情况 B 为什么是爆鸣：采样边界错位

FIFO 存的是 I2S 总线上的**原始字节**。24-bit 立体声 I2S 的格式是每个采样 3 字节，左右交替：

```
I2S 数据在 FIFO 中的字节排列（每个格子 1 字节）:

┌────────┬────────┬────────┬────────┬────────┬────────┐
│L0_byte0│L0_byte1│L0_byte2│R0_byte0│R0_byte1│R0_byte2│  ...
└────────┴────────┴────────┴────────┴────────┴────────┘
│←──  一个左声道采样 (24bit)  ──→│←──  右声道  ──→│

SMPL2PKT 从 R 开始，每 3 字节拼接为一个采样，交替分配左右声道
```

**正常时**，R 恰好指向 `L0_byte0`（采样起始边界），读出的是正确的采样值。但 R 在 `cdn_dp_disable()` 切断时钟时随机停止，可能停在任意字节位置。

**R 停在字节 2（比如 L0_byte2 之后）时**，SMPL2PKT 从 `R0_byte0` 开始读：

```
FIFO:
┌────────┬────────┬────────┬────────┬────────┬────────┐
│L0_byte0│L0_byte1│L0_byte2│R0_byte0│R0_byte1│R0_byte2│L1_byte0│...
└────────┴────────┴────────┴────────┴────────┴────────┴────────┘
                              ↑
                             R 停在这里（断电瞬间的随机位置）

SMPL2PKT 认为这是第一个采样的开始:
  采样 0 = [R0_byte0][R0_byte1][R0_byte2]  ← 恰好完整，没出错
  采样 1 = [L1_byte0][L1_byte1][L1_byte2]  ← 恰好完整，没出错
  ...
  这种情况: 正常! (只是左右声道起始位置错了，人耳基本听不出)
```

**R 停在字节 1（L0_byte1 之后）时**——这才是爆鸣的来源：

```
FIFO:
┌────────┬────────┬────────┬────────┬────────┬────────┐
│L0_byte0│L0_byte1│L0_byte2│R0_byte0│R0_byte1│R0_byte2│L1_byte0│...
└────────┴────────┴────────┴────────┴────────┴────────┴────────┘
                  ↑
                 R 停在这里

SMPL2PKT 强行拼接:
  采样 0 = [L0_byte2][R0_byte0][R0_byte1]
           ↑ 左声道的高位字节  ↑ 右声道的低两个字节
           = 两个不同采样拼出来的值，没有任何音频意义
           
  采样 1 = [R0_byte2][L1_byte0][L1_byte1]
           = 又一个拼接怪胎
```

**为什么拼接出来的值就是爆鸣**：

24-bit PCM 采样值的范围是 -8388608 ~ +8388607。正常音频（比如一段轻柔的人声）的连续采样值变化平缓，比如：

```
... 1234, 1250, 1245, 1260, 1255 ...  (相邻采样差 ~10-20)
```

但当字节边界错位后，拼接出来的"采样"可能是：

```
... 1245, 4893721, -72341, 8156900, ...  (相邻采样差 ~数百万)
```

在 DAC 的输出端，这意味着电压从接近 0V 瞬间跳到接近 Vmax——这个陡峭的阶跃就是**爆鸣声**的物理本质。它不是"播放旧音频"，而是**字节边界错位制造了数学上不可能的采样值**。

更糟的是，错位是**持续性的**：一旦 R 从错误字节开始读，后面每一个采样都是错位拼出来的。一连串的随机大振幅值 = 一连串的爆裂声。

### 情况 C 为什么是无声：FIFO 读空

FIFO 硬件的空判断条件是 `R == W`（读指针追上了写指针）。当 SMPL2PKT 读得比 AIF 写得快，R 追上 W 时，FIFO 返回全 0。

重插场景下，如果 R 在断电时停在了一个**比 W 初始值大**的位置：

```
FIFO 地址:  0     1     2     3     4     5     6     7
         ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
         │     │     │     │     │     │     │     │     │
         └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
                            ↑                   ↑
                       W = 3 (刚启动)        R = 6 (断电残留)

FIFO 硬件判断: W=3, R=6, 差值 = (6-3) mod 8 = 3 entries "有效"
但实际上: W 只写了 0,1,2 三个位置，位置 3,4,5 还没被写过
```

当 SMPL2PKT 从 R=6 开始读，读完 6,7,0,1,2 之后，R 和 W 都变成 3，FIFO 判定为空。

但在这之前读出的 6,7,0,1,2 是什么？这取决于断电前和加电后的状态：
- 如果 FIFO 掉电后清零：读出全 0
- 如果 FIFO 保留了旧值：读出的是重插后 AIF 采样的第一段数据——但这些数据恰好是"旧音频流末尾 + 新音频流开头"的拼接

无论哪种，读出值最终会趋向全 0（R 追上 W → FIFO 空 → 输出 0）。

**24-bit PCM 全 0 = 采样值为 0 = DAC 输出中点电压 = 无声**。

这就是为什么 `R > W` 导致无声而非爆鸣：要么从一开始就读空 FIFO（全 0），要么很快就读完残留数据进入空状态（短暂有声然后静音）。

---

**"有概率"的本质**：R 停在哪个字节取决于断电瞬间 I2S 传输的相位（随机的）；W 初始化到哪里取决于硬件上电行为（可能 0、可能保留、可能随机）。两者叠加导致三种结果随机出现。

## 四、为什么驱动完全不知道

```
中断路径:

APB 顶层:
  APB_INT_MASK (0x6c) = 0     ← Mailbox + PIF 中断已使能
  APB_STATUS_MASK (0x70)      ← 从未读取

PIF 子层:
  SOURCE_PIF_INTERRUPT_SOURCE (0x30824)  ← 从未读取
  SOURCE_PIF_INTERRUPT_MASK   (0x30828)  ← 从未写入 (默认全屏蔽)

FIFO 状态:
  FIFO_STTS (0x3008c)         ← 从未读取
  AUDIO_PACK_STATUS (0x2298)   ← 从未读取
```

驱动定义了寄存器地址，但没有定义任何 FIFO 溢出/下溢的 bit 位定义。对比同一个内核中其他 Rockchip 驱动：

[rk3066_hdmi.h](kernel/drivers/gpu/drm/rockchip/rk3066_hdmi.h#L220)：
```c
HDMI_INTR_AUDIO_FIFO_FULL = BIT(4),  // ← 有明确的 FIFO 满中断位
```

[rk628_gvi.c](kernel/drivers/gpu/drm/rockchip/rk628/rk628_gvi.c#L166-L167)：
```c
INTR_EN_INTR_AFIFO_OVERFLOW_EN  = BIT(10),  // ← 有明确的溢出中断
INTR_EN_INTR_AFIFO_UNDERFLOW_EN = BIT(11),
```

但 CDN-DP 的 `SOURCE_PIF_INTERRUPT_SOURCE` 对应的 bit 位定义**根本不存在于驱动代码中**。FIFO 异常检测和恢复被完全委托给了闭源的 firmware（`rockchip/dptx.bin`），host 侧零感知、零处理。

## 五、为什么一次坏了就一直坏到下次拔插

FIFO 的损坏是**持久性的**——读写指针一旦错位，不会自动恢复：

```
正常状态:
  ┌─────┬─────┬─────┬─────┬─────┬─────┐
  │ A0  │ A1  │ A2  │ A3  │ A4  │ A5  │  ← W 写、R 读，同步推进
  └─────┴─────┴─────┴─────┘     ↑           R 读到的 = W 刚写的
                            W

错位后:
  ┌─────┬─────┬─────┬─────┬─────┬─────┐
  │ ??? │ ??? │ A2  │ A3  │ A4  │ A5  │  ← W 在写新数据
  └─────┴─────┴─────┘     ↑            ↑
                      R (读这里)    W (写这里)
  
  R 读到的 ≠ W 刚写的，永远不一致
```

这种错位只有两个事件能修复：

| 事件 | 做了什么 | 何时触发 |
|------|---------|---------|
| `AUDIO_SW_RST` | W=0, R=0, 清空 FIFO | 只在 `audio_stop()` 中 |
| `cdn_dp_disable() + cdn_dp_enable()` | 时钟断电重来 | 下次拔插 |

当前代码中 `audio_config()` 不写 `AUDIO_SW_RST`（只写 `SYNC_WR_TO_CH_ZERO`），所以即使 ALSA 重新调了 `hw_params`，FIFO 的错位也不会被修复。

---

## 六、修复

在 `cdn_dp_audio_config_i2s()` 和 `cdn_dp_audio_config_spdif()` 的**开头**加两行：

```c
// 修复: 配置音频通路前先复位 FIFO，确保读写指针从零开始
writel(AUDIO_SW_RST, dp->regs + FIFO_CNTL);   // BIT(0): 复位
writel(0, dp->regs + FIFO_CNTL);               // 释放复位
// 然后继续原有的配置序列...
writel(SYNC_WR_TO_CH_ZERO, dp->regs + FIFO_CNTL);
```

注意必须在 `AUDIO_SW_RST → 0 → SYNC_WR_TO_CH_ZERO` 的**同一个配置序列内**尽快完成，因为释放复位后 AIF 时钟仍在运行，W 指针会立即重新开始累加。如果中间隔了很久（比如中间调了 mailbox 消息），W 又绕了好几圈。

对应的原则 4 修复——"硬件复位后无条件重配音频，重配时必须先复位 FIFO"。

## 七、对应设计原则

这个问题违反了文档 [12-dp-audio.md](12-dp-audio.md) 中的**原则 2**和**原则 4**：

- **原则 2**（音频输入时钟不得早于音频通路配置使能）：AIF 时钟在 `clock_reset()` 就开了，此时 FIFO 未复位、解码器未配置
- **原则 4**（硬件复位后无条件重配）：`audio_config()` 没有做 FIFO 复位，假定 W/R 指针处于良好状态

同时也揭示了**原则 3**（无条件副作用）在此处的推广：FIFO 复位是硬操作，`audio_config()` 作为重配入口，无论当前指针状态如何，都应该无条件复位。
